Every large scientific experiment eventually accumulates a great number of software
that can easily become overwhelming for one individual to master. Specialists write
analysis tools to answer their own questions, each with its own conventions, and over
time this becomes a sprawling toolkit that encodes how the experiment is actually
understood. The knowledge of which tool answers which question, with what settings,
lives in the heads of a few experts. A newcomer with a perfectly reasonable question is
often blocked not by the science, but by not knowing where to look.
    The Jiangmen Underground Neutrino Observatory (JUNO), a 20-kiloton liquid-
scintillator detector in China, illustrates this challenge clearly. It was built to study
neutrinos using 17,596 large photomultiplier tubes (PMTs) read out through a multi-
layered electronics chain. The detector is filled and sealed, so the underwater electronics
cannot be physically accessed during operation. Diagnosing faults therefore depends on
the careful analysis of detector data: silent hardware regions, flashing PMTs, abnormal
hit multiplicities, or missing electronics components must be inferred indirectly from
the recorded event stream.
   This thesis investigates whether a locally deployed Large Language Model (LLM)
agent can help physicists perform such diagnostic tasks by translating natural language
questions into a working sequence of analysis tools. Concretely, can a system take a
request like "was this hardware region silent during these events?" and autonomously
decide which analysis tools to run, with what arguments, and in what order. This
process is straightforward for an expert who knows the software ecosystem, but difficult

    The central idea is the Skill Card: a structured description of an analysis tool that
states, in one human-readable file, what the tool does, when it should and should not
be used, what inputs it expects, and what it returns. A Skill Card serves three roles
at once: it is documentation for a physicist, instructions for the AI, and a contract
the software can check automatically. Around this representation, the thesis builds an
assistant that deliberately separates two decisions that small models tend to confuse
when forced to make them together: which tool and when to use it to solve the query,
and how exactly to call it. This assistant, called The Analysis Agent, works through
different nodes. A first node selects the most appropriate tool using compact Skill
Card summaries. A second node loads the full Skill Card, checks whether the choice is
appropriate, and formats the arguments under a type-safe schema. This design directly
addresses common failures of small LLMs, such as choosing a plausible but wrong tool,
confusing argument types, or hallucinating unsupported capabilities. A complementary
memory mechanism lets the assistant keep track of key facts (file paths, hardware
identifiers, anomaly counts) across long investigations without drowning in its own
history.
   Writing a Skill Card by hand for every tool would simply move the bottleneck rather
than remove it. The thesis therefore adds a second subsystem, The Learning Pipeline,
that tries to write Skill Cards automatically, reading a tool’s source code, combining
mechanical code analysis with the language model’s interpretation, and then testing
each draft by handing it back to the assistant to use on realistic queries. A card is
accepted only if it proves usable in practice.
  The system was evaluated on a benchmark, specifically made for this thesis, of 33
JUNO-style diagnostic queries, organized into tiers, and on four extended, multi-step
scenarios, always against a standard agent design using the same tools. On simple, single-
tool questions, both approaches worked well. The advantage of the structured design
emerged on harder tasks: it called tools with consistently higher argument accuracy,
and on the long multi-step diagnostics it completed most investigations that the simpler
agent could almost never finish (16 of 20 runs, against 3 of 20). The results show that
explicit tool metadata, validation, planning, and memory are particularly important
when small local models must perform scientific tool orchestration. Furthermore, a
comparison on the solving abilities of the Analysis Agent was made with automatically
synthesized Skill Cards and performs well comparably to hand-written cards for positive
tool use.
    The work also identifies important limitations. Reliability comes at a cost in speed,
since the assistant thinks in several steps per tool call, and the longest cross-system
diagnoses still exceed what the small model can reliably sustain.

    Overall, this thesis shows that useful scientific agents require more than access to
tools. They require structured descriptions of what tools mean, validation of how they
are called, and memory mechanisms that preserve context across multi-step reasoning.
Within the scoped JUNO diagnostic setting, the proposed architecture demonstrates
that locally deployed LLM agents have the potential to become practical assistants for
scientific computing workflows.

Introduction

1.1      Context and Motivation
The Jiangmen Underground Neutrino Observatory (JUNO) is a multi-purpose neutrino
experiment whose central detector instruments 17,596 large photomultiplier tubes
(PMTs) read out by a hierarchical electronics chain of mainly Global Control Units
(GCUs), Back-End Cards (BECs), and Reorganise and Multiplex Units (RMUs). Once
the detector is sealed and filled, no component in the underwater front-end can be
physically accessed for the projected 20-year operational lifetime [1]. The sole means
of detecting and localising hardware anomalies is the statistical analysis of the data
stream itself.
   This diagnostic work is supported by a growing ecosystem of analysis tools developed
by detector experts within the JUNO collaboration. These tools encode domain
knowledge about the hardware hierarchy, run conditions, and data quality metrics.
Tools can be written independently, with their own conventions for input formats,
parameter names, default values, and output structures. No tool was designed with the
assumption that an automated system would parameterise or invoke it.
   Using this tool suite effectively requires substantial human expertise. A physicist
diagnosing a potential hardware fault must know which tools exist, select the appropriate
one for the current question, provide the correct file paths and parameter values, interpret
the output in context, and often chain the result into a following query: for example,
identifying an outlier PMT, looking up which GCU it belongs to, and then checking
whether that GCU’s parent RMU was active during the run.
   Recent progress in large language models (LLMs) has enabled a new type of au-
tonomous software systems, AI Agents. In this thesis, an AI agent is not a detector-
control system. It is a software assistant built around a LLM. Its role is to decide
which tool1 to call next, with which arguments, and how to use the returned result to

answer the user (Section 2.2). The reasoning capabilities of modern LLMs, combined
with structured function-calling interfaces, make it possible in principle to bridge the
gap between a physicist’s question and the programmatic execution of the relevant
diagnostic pipeline.
     However, generic agent frameworks are not directly suited to the constraints of a
large physics experiment. Some requirements distinguish this setting from the typical
tool-use benchmarks in the LLM literature. First, the tool library is heterogeneous
and growing. They have overlapping scopes, inconsistent interfaces, and no central
registry. An agent must be able to discriminate between semantically similar tools
and must accommodate new tools without requiring manual prompt modifications or
retraining. For example, one tool may search for globally noisy PMTs, while another
may inspect the time profile of one selected PMT. Both are relevant to a question such
as “is this PMT abnormal?”, but they answer different diagnostic questions. Second,
reliability requirements are high: a diagnostic conclusion that is confidently wrong can
be worse than no conclusion at all. Third, the project was constrained to the use of
small language models deployed on restricted hardware (around 8 to 30B parameters)
to answer the possible need of data privacy but also due to infrastructure constraints.
It limits the available models to open-weight LLMs, which are substantially less capable
than frontier cloud-hosted models on structured reasoning and function calling tasks.


1.2        Problem Statement and Research Questions
The central challenge addressed by this thesis can be stated as follows. An AI agent
based on a small LLM that orchestrates scientific analysis tools requires structured
knowledge about each tool: what it does, when it should be used, what arguments
it expects, and what it returns [2]. In this work, this knowledge is captured in Skill
Cards: typed, human-readable YAML2 documents that serve simultaneously as tool
descriptions for the agent, input contracts for argument validation, execution manifests
for dynamic invocation, and editable documentation for the physicists. Skill Cards
address this representation problem by making tool interfaces, usage boundaries, and
expected outputs explicit. But they also need to be autonomously written to lower the
barrier of entry for a user that would not want to bother writing a specific Skill Card
from the ground-up.
    Furthermore, a static, purely prompt-engineered agent may not exploit complex
multi-step toolchains reliably, particularly on the constrained local models available in
this work.

1.3     Contributions
This thesis makes the following contributions:

  1. The Skill Card abstraction: a type of "identity card" for each analysis tool,
     implemented as a typed, machine-validated YAML schema. It captures tool
     identity, parameter contracts, usage policies, execution details, and output schemas
     in a single human-readable document, decoupling tool knowledge from both the
     agent’s reasoning logic and the tool’s source code.

  2. A Select-then-Validate agent architecture: a runtime agent based on Lang-
     Graph that first chooses which tool seems relevant, then a separate validation step
     checks whether this choice and its arguments are appropriate before execution.

  3. Folded Memory: a structured memory management system that combines a
     findings list with a periodically compressed narrative summary, mitigating context
     degradation during long investigations.

  4. An automated Skill Card synthesis pipeline: an offline LangGraph pipeline
     that ingests a raw Python function, combines AST-based static analysis with
     LLM-based code tracing, drafts a Skill Card, and validates it through a testing
     protocol (the Gauntlet) with a targeted refinement loop.

  5. A tiered evaluation benchmark: a suite of 33 diagnostic queries across 4
     tiers (numbered 1,2,3,5) plus four long-horizon scenarios (Tier 4), with ground-
     truth tool selections and expected arguments, designed to measure tool selection
     accuracy, argument correctness, and multi-step task completion under controlled
     conditions. This benchmark is used to validate the capabilities of the designed
     architecture.

  6. Empirical evaluation: a systematic comparison of the full JUNO agent against
     a standard ReAct baseline on the tiered benchmark and on long-horizon diagnostic
     scenarios, and a quantitative comparison of agent performance when operating
     with hand-written versus automatically synthesised Skill Cards.

1.4      Scope and Constraints
Several boundary conditions shape the work presented in this thesis.
    The system is currently designed for offline diagnostic support: answering questions
about completed or ongoing runs after data has been collected and preprocessed. It does
not operate at DAQ (data acquisition) latency and is not intended to replace real-time
monitoring infrastructure. The LLM inference time, which ranges from tens of seconds
to several minutes per query depending on task complexity, is the dominant bottleneck.
The orchestration architecture itself introduces negligible overhead relative to the LLM
calls. Extending the system toward online monitoring is a plausible future direction, but
it would require either substantially faster local inference or a fundamentally different
triggering mechanism, and is not claimed as a current capability.
    All experiments are conducted using locally deployed open-weight models (GPT-OSS-
20B) running on consumer-grade hardware. This is a deliberate constraint. The results
reported in this thesis should therefore be read as results for the class of open-weight
models that are deployable in a restricted-access scientific computing environment, not
as a statement about what is achievable with frontier model access. The architectural
contributions (Skill Cards, the validation gate, Folded Memory) are independent of
the model and would benefit from stronger underlying models, but the quantitative
performance figures are specific to the model tier used.
    The tool suite used for development and evaluation is composed of tools provided
by the thesis supervisors, representative of real JUNO diagnostic practice, and tools
developed during this thesis work to achieve sufficient diversity for benchmarking.
These tools operate on realistic JUNO data (derived from filling-test runs via C++
preprocessing into a simplified CSV format) and respect the hardware nomenclature
of the experiment, but they are not claimed to represent the full scope of production
diagnostics performed by JUNO physicists. Their role is to provide a controlled,
executable tool suite over which the agent’s capabilities can be systematically evaluated.

Background and Related Work

2.1     The JUNO Detector: Technical Background
The Jiangmen Underground Neutrino Observatory (JUNO) is a large-scale liquid
scintillator neutrino experiment is located in Guangdong Province, southern China, at
a depth of approximately 650 m underground and started physics data taking on 26
August 2025 and [1][4]. Its primary physics goal is the determination of the neutrino
mass ordering through precision measurement of the oscillation pattern of reactor
antineutrinos produced at two nuclear power plants located approximately 52.5 km away.
Achieving this requires an unprecedented energy resolution of at least 3% at 1 MeV,
which in turn imposes tight requirements on the detector design and components in the
detector readout chain. This section describes that chain in sufficient depth to motivate
the diagnostic tooling and monitoring requirements that this thesis addresses.


2.1.1     Detector Geometry and the Photosensor System
The JUNO central detector consists of 20 kt of liquid scintillator (LS) contained in
a spherical acrylic vessel of 35.4 m diameter, itself immersed in a large water pool.
Scintillation photons produced by neutrino interactions in the LS are collected by a
dual calorimetry photosensor system [1]:

  • 17,596 Large PMTs (LPMTs), 20-inch diameter, providing the primary calori-
    metric measurement through full waveform sampling. These are the central
    concern of the readout electronics described in the remainder of this section.

  • 25,587 Small PMTs (SPMTs), 3-inch diameter, interwoven between the
    LPMTs and operating in a photon-counting mode to provide an independent
    cross-calibration of the energy response.

   Together, this dual system achieves a photon sensor coverage exceeding 75%, a
fundamental prerequisite for the target energy resolution. The LPMTs are individually

(UWB) via coaxial cables. Once the detector is filled and sealed, neither the PMTs

2.1.2     The Trigger System Hierarchy
The JUNO large-PMT trigger system is organised into a hierarchy that spans from
individual PMTs down to the central data acquisition system [4, 5]. Figure 2.2 provides
a schematic of this chain.


Photomultiplier Tube (PMT). When photons coming from the interactions in the
detector are detected by a LPMT, their corresponding channel forms a negative pulse
(waveform). Offline waveform-reconstruction extracts per-channel observables such as
the photon hit time and the collected charge [7].

            Figure 2.2: Scheme of the JUNO trigger system. Taken from [6]

Global Control Unit (GCU). The GCU is one of the core electronics module [5].
Each GCU is responsible for exactly three LPMTs. It performs the digitalization of the
waveforms, the generation of local triggers, the reconstruction of the time and charge
information and they also send the PMT waveform data to the DAQ during an accepted
trigger decision.
    The GCU are located inside the UWB and communicates with the back-end elec-
tronics over CAT6 Ethernet cable of approximately 100 m [7]. There are 5878 GCUs
for the central detector (one per three LPMTs). A GCU that fails silently renders its
three associated PMTs unreadable without any external hardware indicator.


Back-End Card (BEC). The BEC is the outside-water concentrator board that
interfaces the underwater front-end (UWB/GCU) to the trigger/clock system. Each
BEC collects trigger primitives from up to 48 GCUs (corresponding up to 144 PMTs),
sums them, and forwards the result toward the global trigger. It also distributes a
62.5 MHz synchronisation clock to all connected GCUs, ensuring temporal alignment
across the detector [4]. Around 123 BECs are required for the central detector [8].


Reorganise and Multiplex Unit (RMU). The RMU aggregates signals from up to
21 BECs and serves as the interface between the distributed GCU/BEC network and the
Central Trigger Unit (CTU) [7]. It hosts three mezzanine cards and is responsible for
clock distribution, trigger routing, and data multiplexing. In the nomenclature adopted
within this thesis and in the diagnostic tools it describes, an RMU is identified by a
composite index of the form X-Y (e.g. 5-1), where X denotes the RMU board number
and Y the mezzanine slot. A single RMU therefore supervises a well-defined sub-volume
of the detector. Silence or instability at the RMU level implies the simultaneous loss of

all PMT channels in that sub-volume.


Central Trigger Unit (CTU). The CTU receives trigger primitives from all RMUs,
computes a global trigger decision by comparing the total summed hit count against a
configurable threshold, and distributes a validated trigger signal back to all GCUs with
a timestamp via the RMU/BEC chain [4]. Upon receiving a global trigger, each GCU
transmits the buffered waveform data to the DAQ event builder.


2.1.3     Run Structure and the Diagnostic Data Format
The native JUNO data format is a ROOT-based binary stream produced by the DAQ
event builder and processed by the JUNO offline software (JUNOSW) [4, 9]. Raw data
is first converted to a ROOT-based format (RTRAW), then passed through an Online
Event Classification (OEC) system which selects between full waveform storage and
compressed time-charge (t/Q) storage depending on event type [9]. The resulting data
stream is estimated at approximately 60 MB/s, amounting to several petabytes per
year [9]. Monitoring the quality of this stream is the responsibility of JUNO’s dedicated
Data Quality Monitoring (DQM) system [10], which reconstructs raw data directly from
the DAQ and applies event visualisation and per-channel metrics to detect anomalies
during data-taking.
    For the purposes of this thesis, the production ROOT format is not directly suitable
as a benchmarking substrate. The agent system developed here is intended to be
evaluated on realistic but self-contained diagnostic scenarios; requiring evaluators to
maintain a full JUNOSW installation and process large ROOT files would make the
benchmark environment impractical to reproduce and extend. The test data used in this

was preprocessed with JUNO-specific C++ extraction code into a simplified flat tabular
format. Each row in the resulting CSV file corresponds to a single PMT hit within

2.1.4      Operational Diagnostics: Motivation and Scope

The hardware hierarchy and data format described above define the operational context
that motivates this work. Because the front-end electronics is permanently inaccessible
once the detector is sealed, the only available means of detecting and localising hardware
anomalies is through the statistical analysis of the data stream itself. Physicists and
detector operators must answer questions related to the acquisition of data depending
on the hardware, for example:

Is RMU 4-1 fully operational? Did all its connected GCUs and BECs contribute hits,
or is a sub-section of the detector silent?

Answering these types of questions requires selecting the appropriate analysis tool from
a growing suite, providing it with the correct file paths, parameter values, and hardware
identifiers, interpreting its output, and often chaining the result into a subsequent query.
For example, identifying a problematic GCU, tracing which RMU it belongs to, and
then verifying whether that RMU was active during a specific series of events. Today,
this process requires expert knowledge of both the detector hardware hierarchy and the
available software tooling. The central ambition of this thesis is to evaluate whether an
AI agent can automate this diagnostic workflow from a natural language query.
    A key design requirement that follows directly from this operational context is that
the agent must be able to integrate tools written by physicists who authored the tools
independently and without any consideration for how an AI system might invoke them.
In this work, the tool suite used for development and evaluation is composed of two
distinct parts. The first consists of tools provided by the thesis supervisor, written
by members of the JUNO collaboration and representative of real diagnostic practice
within the experiment. The second layer consists of tools developed in the course of
this thesis work, written specifically to extend the suite to a diversity sufficient for
benchmarking. While these tools operate on realistic JUNO data and respect the
hardware nomenclature described in the preceding sections, they are not claimed to
represent the full scope of diagnostics performed by JUNO physicists, nor to meet the
standards of production analysis software. Their role is instrumental: to provide a
controlled, executable tool suite over which the agent’s orchestration and tool-learning
capabilities can be systematically evaluated.



2.2      Large Language Models and Autonomous Agents

2.2.1     How Large Language Models Work
Large Language Models (LLMs) are the computational substrate on which the agent
system described in this thesis is built. This section provides a functional description
of how they work. The goal is to establish the conceptual vocabulary that will be used
throughout the rest of this chapter and thesis.


The basic unit: tokens and probability. An LLM does not process raw characters
or words. Instead, it operates on tokens: sub-word units produced by a fixed vocabulary
of varying entries (e.g., GPT-2 uses 50,257 vocabulary tokens) [11]. Common English
words are usually single tokens, while rarer words or technical identifiers are split into
several. The string PMTID might be represented as two tokens, PMT and ID, while the
is a single token. This tokenisation is fixed at training time and is a property of the
model.

                                            11
CHAPTER 2. BACKGROUND AND RELATED WORK


      At its core, a typical LLM is a function that maps a sequence of tokens to a
probability distribution over the next token [12]. Formally, given a sequence of tokens
t1 , t2 , . . . , tn , the model assigns a probability P (tn+1 | t1 , . . . , tn ) to every token in its
vocabulary. Text is generated by sampling from this distribution repeatedly: the model
predicts the next token, appends it to the sequence, predicts the token after that, and
so on until a stopping condition is reached. This autoregressive process is the same
whether the model is answering a physics question, writing Python code, or producing
a JSON object. The generation mechanism is identical in all cases. What changes is
the input, which steers the distribution toward different regions of the output space.
    An LLM assigns higher probability to token sequences that are more consistent with
the patterns seen during training. A temperature parameter T controls how peaked or
diffuse the sampling distribution is: at T → 0, the model always selects the single most
probable token (deterministic). While at higher T , it samples more broadly, producing
more varied but potentially less coherent output.


The architecture: transformers and self-attention. The dominant neural ar-
chitecture underlying most modern LLMs is the Transformer [13]. Functionally, its
defining primitive is self-attention, which computes interactions between tokens across
the entire input sequence within each layer. Self-attention connects all positions with a
constant number of sequentially executed operations, enabling parallel processing of a
fixed input sequence and shortening the computational path between distant tokens.
In principle, this allows the model to condition on relationships between distant spans
of text, linking "RMU 5-1" early in a prompt with "silent" much later, supporting
long-range dependencies that are valuable for long-context task execution .
    The scale of these models is significant. The number of parameters in most used
modern LLMs ranges from a few millions and can go up-to trillions. The model used
has 20B parameters. This size tier is runnable on local high-range consumer hardware
but below the capability frontier of the largest cloud-hosted models. This constraint
is a recurring theme in the architectural decisions. Figure 2.3 gives a schematic view
of the decoder-only architecture used by modern autoregressive LLMs. The diagram
abstracts away implementation details but retains the components most relevant to
tool calling and next-token generation.


Training: pre-training and instruction tuning. LLMs are trained in two phases [2,
14]. In the first phase, pre-training, the model is trained on a very large corpus of text
(hundreds of billions to trillions of tokens drawn from the web, books, code repositories,
and scientific literature) using the simple objective of predicting the next token. This
phase produces a model with broad world knowledge and linguistic competence but no
particular tendency to be helpful or to follow instructions.

                                                  12
                   2.2. LARGE LANGUAGE MODELS AND AUTONOMOUS AGENTS

    The second phase, instruction tuning (or fine-tuning with human feedback), shapes
the model’s behaviour toward that of a useful assistant. The model is trained on curated
datasets of (instruction, response) pairs, with reinforcement learning from human
feedback (RLHF) used to align its outputs with human preferences [14]. After this
phase, the model responds to natural language instructions, maintains a conversational
register, and declines requests that are out of scope. The model used in this work has
undergone this process and is typically referred to as chat model or instruction-following
model.
   It is important to understand that the training does not make the model learn a
database of facts, or an explicit set of rules. It learns a very high-dimensional statistical
manifold of token patterns. Its apparent knowledge of physics, chemistry, or software
engineering is the result of that statistical structure, not of a factual source. This
has direct consequences for reliability in scientific contexts, which are discussed in
Section 2.2.3.

The context window Perhaps the most operationally important concept for this
thesis is the context window. The context window is the finite sequence of tokens that
the model can attend to simultaneously during a single inference call [2]. Everything
the model "knows" during a given response must be present in this window: the system
instructions, the conversation history, the tool descriptions, the tool outputs, and the
current query. There is no implicit persistent memory across calls. When the context
window is cleared, between conversations or when it is deliberately trimmed, the model
has no recollection of what preceded it.
    The size of the context window is dependent on the model and has grown substantially
over recent generations. Early models had windows of 2,048 tokens while current models
can support up to one million tokens. However, for the locally deployed models used
in this work, the context window is smaller (128k tokens for GPT-OSS 20B), and
operational costs scale with its length. A prompt containing 17,596 PMT identifiers,

                                             13
CHAPTER 2. BACKGROUND AND RELATED WORK


the full history of a ten-step diagnostic workflow, and the descriptions of thirty available
tools would easily exceed practical limits. Furthermore, empirical studies show that
effective performance can degrade as input length grows, even when the model can still
retrieve the relevant evidence. This implies that the effective context is smaller than
the nominal token limit, and that long prompts can dilute reasoning performance [15].
This is one of the main constraint on the agent, different methods were designed to
precisely address this.


In-context learning and prompt engineering. An important property of large
pre-trained models is in-context learning: the ability to perform a new task correctly
based solely on examples or instructions provided in the context window, without any
modification to the model’s weights [12]. A model that has never been explicitly trained
on a JUNO-specific task can still answer JUNO diagnostic queries correctly, provided
the context window contains a sufficiently detailed description of the task, the available
tools, and the expected output format. This is the foundational property that makes
the Skill Card approach of this thesis viable. The model is not retrained for JUNO;
it is given structured descriptions of tools at inference time, and learns to use them
in-context.
    The practical implication is that the quality of the input (the prompt) is a primary
determinant of model behaviour. Prompt engineering is the practice of designing inputs
to elicit reliable, accurate, and appropriately formatted responses. In this work, prompt
engineering is systematic : the agent’s prompts are structured templates with clearly
delineated sections for skill summaries, memory, plan state, and recent history. The
concrete prompt templates used by the graph nodes, and the design principles behind
them, are discussed in Appendix D.
    A specific and powerful prompting technique relevant to this work is chain-of-thought
(CoT) prompting [16], in which the model is encouraged to produce intermediate
reasoning steps before arriving at a final answer. In the agent context, this manifests as
the thought field in the AgentDecision schema (Section 3.3.3): the model is required
to articulate its reasoning for selecting a tool before the selection is executed. This
serves a dual purpose, it improves selection accuracy for smaller models by forcing
deliberation, and it produces an explicit reasoning for the user.


2.2.2     Tool-Using Agents
In-context learning (Section 2.2.1) allows an LLM to follow instructions and produce
structured outputs, but it cannot on its own go beyond the information present in the
context window. While an LLM reasoning about a JUNO dataset of events can describe
what a flashing PMT is, it cannot tell whether PMT 4258 is flashing in a specific series

                                            14
                  2.2. LARGE LANGUAGE MODELS AND AUTONOMOUS AGENTS


of events unless the relevant data has been computed and placed in front of it. AI
Agents close this gap by coupling the LLM’s reasoning capability with the ability to
invoke external tools (python scripts in the case of this thesis) and incorporate their
outputs into subsequent reasoning steps. This section describes the basic agent loop
and the two frameworks used in this work: the ReAct pattern, which serves as the
baseline, and LangGraph, which is the implementation base of the full system. The
cognitive demands from this design are described in 2.2.3

Basic agent loop. The fundamental operation of a tool-using agent can be described
as a loop over three stages [17, 18]:

 (1) Observe: The agent receives the current state of the conversation: the original
     user query, any instructions provided in the system prompt, the descriptions of
     available tools, and the accumulated history of prior actions and their outputs.

 (2) Decide: The LLM, conditioned on this context, decides what to do next. This
     decision is one of two types: either invoke a specific tool with specific arguments,
     or produce a final answer and terminate. In structured-output mode, this decision
     is emitted as a validated object rather than free text, ensuring deterministic
     parsing and type validation by the surrounding software.

 (3) Act: If the decision is a tool call, the surrounding framework executes the
     designated function with the extracted arguments, captures the return value, and
     appends it to the context window as a new observation. Control then returns to
     stage (1).

This loop continues until the agent emits a final answer. The number of iterations is
not fixed in advance; it is determined dynamically by the agent’s assessment of whether
the accumulated information given by its own knowledge or the knowledge acquired by
using the available tools is sufficient to answer the original query.

The ReAct pattern. The most widely adopted framework for tool-using agents is
ReAct [18], introduced by Yao et al. at ICLR 2023. ReAct stands for Reason + Act,
and its central insight is that reasoning traces and tool actions should be mixed rather
than separated: before each action, the model generates an explicit thought (a free-text
articulation of its current understanding of the task and its reasoning for the next
action). After receiving the tool output, it generates another thought before deciding
on the next action. The loop is therefore:
The explicit thought step serves two purposes. Practically, it improves task performance
on models of moderate capability by forcing deliberation before commitment, miti-
gating impulsive tool selection. The original paper demonstrates that ReAct reduces

hallucination and error propagation relative to chain-of-thought prompting alone, by
grounding the reasoning in verified external observations rather than the model’s inter-

operator needs to understand and verify the diagnostic conclusion.
    ReAct is intentionally simple. It makes no assumptions about the number of tools,
the structure of the task, or the nature of the tool outputs. The entire agent state
is encoded in the growing message history. There is no explicit plan, no structured
memory, and no separation between the high-level reasoning step (what should I do
next?) and the low-level formatting step (what exactly are the arguments?). This
simplicity is its strength as a baseline and its limitation as a production system. In this
work, a standard LangChain ReAct agent [19] is implemented as the baseline against
which the full JUNO agent architecture is compared (Chapter 4). The comparison is
designed to isolate the specific contributions of the architectural additions over the
plain ReAct loop and is further explained in Sub-section 3.3.6.

LangGraph as an implementation framework. LangGraph [20] is an open-source
Python library, developed by the LangChain team, for building stateful agent workflows
as explicit directed graphs. It is the base of the full JUNO agent system developed
in this thesis, and it is worth describing its core abstractions here, as they appear
throughout the system description in Chapter 3.
   LangGraph decomposes the simple ReAct loop into nodes and edges (routes between
nodes): one node selects a tool, another validates arguments, another executes the tool,
and another compresses memory. Furthermore, it adds a critical feature : the state, an
object that is passed as input to every node and updated by its output. It functions as
the agent’s working memory; in this thesis it carries the message history, the current
plan and any other information that must persist across steps.
Thus, LangGraph was selected because it provides a structured graph-based orchestra-
tion model with support for cyclic execution, persistent state, and modularity. While a
similar system could be implemented using custom Python state machines, LangGraph
implements most of the need for the architecture. Furthermore, it provides built-in
checkpointing: the full agent state can be persisted at each step, enabling reproducible

debugging and trace logging via LangSmith [20].

2.2.3     Fundamental Limitations in Scientific Contexts
There are many conditions for designing a reliable autonomous agent in a scientific
setting. Several fundamental limitations become important in a demanding environment:
long multi-step tasks, heterogeneous tool catalogues, data-dependent replanning, and
restricted computing environments. This section enumerates those known limitations
and states their concrete consequences that appeared during the development of this
work. The architectural responses to these limitations are developed in Chapter 3.


Hallucination. Hallucination is the generation of fluent, confident text that is fac-
tually incorrect or entirely fabricated. It is the most widely discussed failure mode of
LLMs [22]. In a conversational setting it is a nuisance; in an autonomous multi-step
agent it is a cascading failure. If the model fabricates a PMT identifier in step 2
then every subsequent step that builds on that claim will be internally consistent but
factually wrong. The final answer will be a coherent narrative about an imaginary
anomaly.
    The root cause is architectural: the LLM is a conditional probability distribution over
tokens, not a database. It does not retrieve facts; it generates text that is statistically
likely given the context. When the context is long and the relevant fact has low attention
weight, the model may generate a plausible substitute rather than reproduce the correct
value.

                                            17
CHAPTER 2. BACKGROUND AND RELATED WORK


Type confusion in argument extraction. A subtler but pervasive failure mode
is type confusion: the LLM extracts the correct semantic value from the context but
represents it in the wrong Python type. This is a direct consequence of operating
entirely in a text domain, where the integer 4258 and the string "4258" are visually
identical. The distinction becomes consequential at the function call boundary. A tool
performing a comparison such as df[’PMTID’] == "4258" against an integer-typed
column will return an empty DataFrame with no exception and no error message. The
agent, observing an empty result, may conclude that the PMT has no hits and declare
it dead, when in fact the query was malformed.
   Type confusion during argument generation is a common failure mode in tool-
augmented LLM systems [23]. Recent benchmarks show that even state-of-the-art
models frequently produce incorrect or misaligned arguments when composing structured
tool calls, particularly in multi-step or nested API sequences. For smaller local models,
which exhibit weaker instruction-following and schema adherence, these error rates are
typically higher.


Tool selection ambiguity and the distraction problem. When an agent has
access to a catalogue of tools, selection ambiguity arises whenever two or more tools
have overlapping descriptions but different operational semantics. In the JUNO context,
consider the following pair: detect_global_occupancy_outliers, which computes
outliers across batch of events, and get_pmt_profile, which retrieves the hit time
series for a single specified PMT. A query such as “is PMT 4258 abnormally noisy?”
is plausibly handled by either tool. The first reveals whether PMT 4258 appears in
the global outlier list; the second shows its detailed per-event behaviour. Selecting the
wrong one does not produce a crash but it produces an answer to a subtly different
question, with no indication that the selection was incorrect.
    This is the distraction problem [24]: the presence of a semantically plausible but
incorrect tool in the catalogue causes the agent to select it instead of the correct one.
The severity of the problem scales with catalogue size. A registry of five tools poses
no challenge to a capable model but a registry of fifty tools with semantically similar
clusters creates systematic confusion, particularly when the model’s available context
for each tool is limited to a short description.


Context degradation over long traces. The lost-in-the-middle effect [15] refers to
the empirical finding that transformer models recall information placed in the middle of
a long input context less reliably than information at the beginning or end. For an agent
executing a ten-to-fifteen step diagnostic, the tool output from step 2 may be effectively
invisible by step 12 as more recent messages occupy the high-attention positions at the
end of the context window. The agent does not signal that it has lost the information;

                                           18
                                             2.3. RELATED WORK AND POSITIONING


it either re-derives it at the cost of additional tool calls, generates a plausible substitute
(hallucination), or silently proceeds with an incorrect value. Furthermore, the increase
of the context causes the agent to have reduced performance[15].

Local inference constraint. One of the constraints of the thesis discussed at the
beginning was the possibility to create an agent on constrained hardware capabilities.
This is not a temporary inconvenience but a fixed boundary condition of the deployment
environment. The best locally deployable models available at the time of writing,
Qwen 3.5 family and GPT-OSS 20B [25], are substantially less capable than frontier
API models on structured reasoning and function calling benchmarks but are far cheaper
to run [26]. The results reported in Chapter 4 should therefore be read as results for
the class of open-weight models that are actually deployable in a restricted-access
scientific computing environment, and not as a statement about what is achievable with
unconstrained model access.


2.3      Related Work and Positioning
The relevant prior work is centered around systems that are structurally adjacent to the
JUNO agent: tool-using LLMs, scientific agents, schema-based tool registries, memory
mechanisms, automatic tool integration, and emerging tool-description standards. This
section reviews these areas and positions the contributions of this thesis within them.


2.3.1     Tool-Using Agent Foundations
The closest architectural ancestor of the JUNO Analysis Agent is the ReAct pattern [18],
already introduced in Section 2.2.2.
    As for the tool use, Toolformer [17] and ToolLLM [24] address it from the training
and benchmarking side rather than the prompting side. Toolformer demonstrates that
tool invocation can be learned through self-supervised data generation; ToolLLM scales
the problem to 16,464 real-world APIs using search over reasoning traces. Both works
establish that tool use can be seen as a learnable capability, and both rely on fine-tuning
the base model. This thesis takes a different route by using in-context tool learning
due to it being easier to implement with the defined constraints.


2.3.2     Domain Specific Scientific Agents
Domain specific scientific agents demonstrate the value of tool orchestration, but most
operate under different assumptions. ChemCrow integrates 18 expert-designed chemistry
tools with GPT-4 across synthesis, drug discovery, and materials design [27]. Coscientist
couples a GPT-4 planner with web search, code execution, and laboratory automation

                                             19
CHAPTER 2. BACKGROUND AND RELATED WORK


commands to design and execute chemistry experiments [28]. CRISPR-GPT applies
the same broad pattern to gene-editing design [29]. The common assumption is that
tool sets are chosen by the system builders, descriptions are written for the agent, and
the target model is a frontier cloud model. These conditions do not hold for JUNO,
where a local model must select among existing Python functions whose authors did
not provide easily readable data for the agent.


2.3.3     Schema-Validated Registries and Decoupled Validation
The Skill Card abstraction has three explicit inspirations : HEP run-card convention,
OpenAI function calling and Anthropic Agent Skills. The comparison is detailed in
Subsection 3.2.4
    Two recent systems converge on related designs. HEPTAPOD, published in Decem-
ber 2025, introduces an HEP orchestration framework for agentic simulation workflows
using schema-validated operations, structured outputs and run-card-driven configura-
tion [30]. AgentFlux, published in October 2025, targets on-device agentic systems
and explicitly decomposes tool calling into selection and argument generation using
decoupled fine-tuning [31]. Both systems appeared after the design phase of the JUNO
architecture, so we treat them as independent convergent designs rather than prior art.
    The convergence is technically informative. HEPTAPOD and the JUNO system
both arrive at typed registries because unstructured docstrings do not scale in scientific
tool catalogues. AgentFlux and the JUNO system both decouple tool selection from
argument generation because small models struggle when asked to solve both problems
in one pass. The implementation paths diverge: AgentFlux fine-tunes adapters, while
the JUNO system assumes no fine-tuning and relies on structured prompts, Skill Cards,
and replanning after failed validations. The overlap validates the Skill Card and Select-
then-Validate patterns under shared constraints without erasing the specific contribution
of this thesis.


2.3.4     Memory and Long-Context Management
Agent memory is a reliability issue, not a convenience feature, and general memory
systems attack the problem through external storage and summarisation. MemGPT
frames the context window as a virtual-memory problem and pages information across
explicit memory tiers [32]. MemoryBank adds long-term memory across sessions,
with mechanisms for storing and updating user-related information [33]. ReadAgent
compresses long documents into gist memories and retrieves the original passages on
demand [34]. DeepAgent compresses the memory in to three separate parts to improve
scalability of their agent [35].
   Folded Memory (Section 3.3.5) draws on the same general principle but is deliberately

                                           20
                                            2.3. RELATED WORK AND POSITIONING


narrower. Unlike MemGPT and MemoryBank, which target open-ended conversational
memory across many domains, Folded Memory is focused on local tasks and designed
for auditable diagnostic evidence.


2.3.5     Automatic Tool Integration and Tool Learning
The closest prior work to RQ2 is LATM, Large Language Models as Tool Makers [36].
LATM uses a stronger model as a tool maker that writes reusable Python utility
functions, and a weaker model as a tool user that calls them on later tasks. It influenced
the context of this thesis, however, the direction is inverted. LATM creates new tools
for recurring reasoning tasks, while the JUNO Learning Pipeline describes existing
tools written by physicists. The executable code is not generated and is not replaceable.
What is synthesized is the structured descriptor that allows the agent to select, validate,
and invoke that existing function.
    Other systems of tool creation are less related. CRAFT creates and retrieves spe-
cialised code snippets for task families, validating generated solutions before abstracting
them into reusable tools [37]. ToolMaker transforms papers-with-code repositories
into LLM-compatible tools by installing dependencies, generating wrappers, and using
closed-loop debugging [38]. Neither learns a typed descriptor for an existing capability
and validates it through agent-in-the-loop integration testing, which is the specific
mechanism of the JUNO Learning Pipeline (Section 3.4).

    The contribution of this thesis is therefore not a general-purpose scientific agent. It

third-party Python tools, validation through agent-in-the-loop integration testing, and
a runtime architecture designed for small local models. No surveyed system provides
that combination under the reliability constraints of a sealed detector electronics chain.

System Design and Implementation

3.1      System Overview and Architecture
The system developed in this thesis has two distinct but coupled systems of use, referred
as the Analysis Agent and the Learning Pipeline. The Analysis Agent system: a physicist
asks a question in natural language and the system decides which existing Python
analysis tools should be called to answer it. The Learning Pipeline: a new Python tool
is added to the tool library and the system prepares the structured description needed
for the agent to use that tool safely.
    Both modes are connected by one object, the Skill Card. A Skill Card is a structured
description of a Python analysis function. It tells the agent what the function does,
when it should be used, what arguments it expects, how it is executed, and what kind
of output it returns. The Analysis Agent is designed to scale, it does not need to
be modified when a new tool is added; it only needs a valid Skill Card for that tool.
Conversely, the Learning Pipeline does not answer physics questions itself, its role is to
autonomously produce Skill Cards that can later be loaded by the Analysis Agent.
   This separation is illustrated conceptually as follows:

                                            ↓
                                  Learning Pipeline
                                            ↓
                                       Skill Card
                                            ↓
                                    Analysis Agent
                                            ↓
                           Tool calls and diagnostic answer

The same structure can also be read from the point of view of a JUNO user. Suppose a
physicist asks:

Development-driven design. The final architecture was not designed in a single

3.2      The Skill Card Abstraction
A Skill Card can be understood as an identity card for a Python analysis tool. Without
it, the agent only sees a function name or a docstring and must guess what the tool does,
how it should be called, and whether it is relevant to the current diagnostic question.
With a Skill Card, this information is made explicit in a format that is both readable
by humans and validated by the software.
   This is important because most of the tools used by physicists were not all written
with an AI agent in mind. They may use different parameter names, default values,
return formats, and implicit assumptions. A human expert can often infer these
conventions by reading the code or by experience. The agent cannot do this reliably
unless the relevant information is provided in a structured way.
     In the implementation, Skill Cards are written in YAML. YAML was chosen because
it is machine-validated, human-readable and human-editable, which matters both for
the manually authored cards and for the user who may wish to inspect or adjust a card
produced by the Learning Pipeline. A Skill Card has five main blocks, described below.


3.2.1     Schema Design
Summary. The summary block contains the information used during the first tool-
selection step : the tool name, a short description, and the declared input parameters.
To assure scalability by reducing context overflow, this block should be concise, because
the agent sees summaries for all available tools at once. Its role is to let the agent form
a first hypothesis about which tool may answer the user’s question.


Execution details. The execution_details block tells the runtime how to call the
underlying Python function. In the current implementation, tools are Python functions,
so this block contains the module path and the function name.


Usage policy. The usage_policy block is the component that most distinguishes a
Skill Card from a standard function-calling schema. It contains two fields: use_when, a
list of scenarios in which the tool is the best choice, and do_not_use_when, a list of
scenarios in which the tool is inappropriate. These fields are written in natural language
and are consumed exclusively by the ArgumentFormatterNode during the validation
step (Section 3.3). Their purpose is to give the agent explicit criteria for judging whether

                                            25
CHAPTER 3. SYSTEM DESIGN AND IMPLEMENTATION


a tool is appropriate. In this thesis, this role is motivated architecturally and examined
through full-system error analysis.


Output schema. The output_schema block describes the structure of the returned
result. This helps the agent anticipate whether a tool will produce the information
needed for the next step.


Skill ID. The skill_id is the unique string identifier, typically matching the function
name.
    Listing 3.1 shows a complete Skill Card for the get_hardware_connections tool,
illustrating how the five blocks work together to provide a description of a tool’s purpose,
interface, invocation mechanism, usage boundaries, and output structure.
    This example also illustrates the main pedagogical role of Skill Cards. They do
not replace the Python functions. They make the assumptions around those functions
explicit enough for an LLM-based agent to use them with fewer selection and argument
errors.


3.2.2     Validation and Runtime Use
Every Skill Card loaded into the system is checked with Pydantic, a Python data-
validation library [39]. First, this means that a card missing required fields, or containing
fields of the wrong type, is rejected before the agent starts using it. Second, the agent
can validated deterministically the tool arguments at runtime. When the LLM proposes
a tool call, the raw argument dictionary is validated against the parameter schema
declared in the Skill Card. This validation checks that required arguments are present
and that values can be interpreted with the expected types. For example, if the model
writes the PMT identifier as the string "4258" while the tool expects an integer, the
validation layer can coerce it to 4258. If the required file path or event range is missing,
the call is rejected before the Python function is executed.
   This addresses the type confusion failure mode described in Section 2.2.3 without
requiring the LLM itself to produce correctly typed values, a task at which smaller
models are unreliable.


3.2.3     Registry Loading
The SkillRegistry loads all YAML Skill Cards from a skill directory when the agent
starts. Valid cards are indexed by their callable name and can then be retrieved by the
Analysis Agent. Invalid cards are logged and skipped, so that one broken card does not
prevent the rest of the system from running.

3.2.4        Comparison to Alternative Representations
The Skill Card draws inspiration from two independent methods. The first is the high-
energy physics convention of the run card: a structured, human-readable configuration
file that encodes domain knowledge about how a piece of software should be invoked.
The second is Anthropic’s Agent Skills framework [40], released in October 2025. Agent
Skills organise tool knowledge into structured folders with a YAML frontmatter block
(a compact descriptor containing a name and trigger condition) and a full instruction
document loaded on demand. The core design principle, which Anthropic terms
progressive disclosure, is that a lightweight summary is always available for discovery
while the full content is retrieved only when the tool is selected, keeping the context
window from growing too much regardless of catalogue size. What distinguishes the
Skill Card from Anthropic’s format is its target: Agent Skills are instruction sets that
teach a model how to perform a workflow; Skill Cards are typed, machine-validated
descriptors that tell a reasoning engine when and with what arguments to invoke a
specific Python function.


Raw docstrings. The simplest possible tool representation is the function’s own
docstring, passed directly to the LLM as part of the tool catalogue. This is the approach1
used by the ReAct baseline in Chapter 4. It requires zero manual effort and is trivially
kept in sync with the code. However, it provides no structured parameter schema (the
LLM must infer argument types from prose), no usage policy (the LLM must guess
when the tool is appropriate), and no output schema (the LLM cannot plan around
what a tool will return). In practice, the absence of type information makes the type
confusion problem more dominant, and the absence of usage boundaries makes the
distraction problem worse as the skill library grows.


OpenAI function-calling schema [41]. The standard for LLM tool descriptions
is the JSON Schema format used by OpenAI’s function-calling API and adopted by
most LLM providers. This format provides a structured parameter schema with types,
descriptions, and required flags which is similar to the summary.parameters block of a
Skill Card. But it does not include any equivalent of the usage policy or the output
schema. The function-calling schema tells the model how to call a tool but not when

3.3      The Analysis Agent

The Analysis Agent is the runtime part of the system that the user interacts with
during a diagnostic session. Its role is not to replace a physicist, but to help structure a
technical investigation. Given a natural-language question, it decides which detector-
analysis tool is relevant, prepares the required arguments, executes the corresponding
tool, records the useful information, and decides whether another step is needed.This
section describes the graph-level architecture, the shared state that flows between
nodes, each node’s responsibilities and implementation, and the different mechanisms
(progressive context disclosure, select-then-validate and folded memory) that manage
the finite context window and the model limited abilities across long-running tasks.

All nodes communicate through a shared state defined as a Python TypedDict named

     needed to decide the next step.

  3. Memory. This is a compressed summary of older results. It containes two sub-

3.3.3       The Select-then-Validate Workflow
The central design choice of the Analysis Agent is the separation between tool selection
and argument formatting into two sequential LLM calls, each with different context.
This two-node design, referred to as Select-then-Validate, addresses a practical failure
mode: tool selection requires awareness of the full tool catalogue and the task, while
argument formatting requires deep knowledge of a single tool’s structure. Packing both
requirements into a single LLM call, as a typical ReAct agent does, forces the prompt to
include the full context of every tool at every step, which both increases context length
and the unreliability of the smaller models used in this work. The Select-then-Validate
design resolves this by giving each node exactly the context it needs and nothing more.
This design increases latency, because one diagnostic step may require two model calls
instead of one.

Agent Node: Planning and Selection

The AgentNode is the system’s central reasoning component. It is invoked at the start of
every agent loop iteration and is responsible for three tasks: reflecting on accumulated
evidence, maintaining the multi-step plan, and deciding what to do next. Its prompt2
is built from several sources of information:

  (i) Skill Summaries: a formatted list of all registered tools, each represented by its
      skill_id and the short description from the Skill Card’s summary block. This is
      the only tool information the AgentNode sees.

 (ii) Folded Memory: the compressed narrative from the FoldedMemory.summary field,
      providing high-level context about what has been tried, what succeeded, and what
      failed across the entire task history.

 (iii) Confirmed Findings: the full FoldedMemory.findings list, providing specific
       facts (file paths, PMT identifiers, anomaly counts) that have been permanently
       recorded and are guaranteed to survive memory compression.

 (iv) Current Plan: the full plan with their current statuses.

 (v) Recent History: the truncated last ten messages from the message list.

   The node returns a structured decision rather than free text; the structured output
permits to reduce stochastic errors. Furthermore, it is completed by Chain-of-thought

improve interpretability: a user reviewing the agent’s diagnostic can read the sequence

Argument Formatter Node: Validation and Argument Construction

Once the AgentNode selects a skill, the ArgumentFormatterNode transforms that deci-
sion into an executable call. It uses the full Skill Card of the selected tool, including
the input schema, descriptions of parameters, and constraints on acceptable values.
    The validation performed here has two levels and is bound by typed Pydantic
models.

   1. Semantic validation. The formatter checks whether the selected skill is appro-
      priate for the user’s request. For example, a plotting skill should not be used when
      the user asks for a numerical comparison unless the plotted result is explicitly
      needed.

   2. Schema validation. The formatter checks whether the arguments match the
      expected interface. This includes required parameters, data types, and default
      values when these are specified in the Skill Card.

    If the proposed action fails validation, the node does not execute the tool. Instead,
it returns a structured error to the AgentNode, which can choose a different tool, repair
the plan, or ask the user for missing information. This validation gate is one of the
main safeguards in the architecture.


3.3.4     Tool Execution
The Tool Node is intentionally deterministic. After validation, it imports the selected
Python function, executes it with the validated arguments, captures the result, and
updates the shared state. The language model is not involved in this step.
     Since, tool functions in the scientific domain return heterogeneous types (e.g. dictio-
naries, Pandas DataFrames, Matplotlib figures, Numpy values) and the message history,
requires all content to be JSON-serialisable strings; there is a need to normalized tool
outputs. It is done by using the normalize_tool_output function that converts the
tool’s return value into a JSON-serialisable structure (e.g. NumPy types are cast to
native Python types).
     The Tool Node also extracts useful findings such as generated plot paths. Any
file paths found are immediately appended to the FoldedMemory.findings list. This

ensures that file paths produced by tools are captured immediately and are available to
the next steps without waiting for the next memory folding cycle, effectively reducing
hallucinations (due to it being done by deterministic code).


3.3.5     Memory Management: Folded Memory
The context window limitations described in Section 2.2.3 become sharp during long
diagnostic tasks. A ten-step investigation that involves scanning a series of events,
identifying outlier PMTs, tracing their hardware connections, and verifying component
activity generates a message history that exceeds the effective attention span of the
models used in this work. An earlier iteration of this work used a three-parts memory
model (episodic, working, tool-output) inspired by [35]. During development, we
observed that the structured plan state already captured most of the working memory
function, making the partition redundant. So, the design converged towards the simpler
two-parts FoldedMemory described below. It is designed through a combination of
structured persistence and periodic compression.


The FoldedMemory Data Structure

This compression is orchestrated by the MemoryFolderNode which is triggered every
five3 tool calls. The FoldedMemory object is a Pydantic model with two fields:


Findings. An append-only list of short strings, each recording a specific fact ex-
tracted from the task history. They are populated by two mechanisms: determinis-
tic path extraction in the Tool Node (immediate) and LLM-based extraction in the
MemoryFolderNode (periodic). The system prompt instructs the AgentNode to trust
findings over the compressed summary for specific values, and to trust them over its
own recollection from the message history. This hierarchy mitigates the hallucination
risk described in Section 2.2.3 and improved success rate during testing.


Summary. A compressed natural language narrative of all steps executed so far, up-
dated at each memory folding cycle. The summary is written by the MemoryFolderNode’s
LLM call and integrates the previous summary with events from the recent message
history. It provides high-level context that helps the AgentNode maintain coherent
planning across the task.
    The separation between findings and summary is a deliberate design choice. Specific,
retrievable facts (IDs, paths, counts) are stored in a structured, machine-scannable
list that the AgentNode can reference precisely. Narrative context (what has been

3.3.6     Comparison to the ReAct Baseline
To contextualise the architectural choices described above, it is useful to enumerate
what the standard ReAct agent used as the baseline in Chapter 4 does not have. The
ReAct baseline is a single-node loop: one LLM call per iteration, receiving the full
tool catalogue, the full message history (untrimmed), and no explicit plan, no folded
memory, no findings list, and no validation gate. The comparison isolates five specific
contributions of the full architecture:

  1. The validation gate (ArgumentFormatterNode) catches selection errors and type
     errors before execution, reducing wasted tool calls.

  2. Progressive context disclosure reduces per-call token cost and focuses each LLM
     call on a single decision type.

  3. The explicit plan provides structured state that survives across iterations and is
     visible to the model at every step.

  4. Folded Memory prevents context degradation over long tasks by compressing
     history into a persistent, structured form.

  5. Skill Cards replace raw docstrings with structured metadata that includes usage
     policies and output schemas, improving selection accuracy in the presence of
     semantically overlapping tools.


3.4     The Learning Pipeline
The Analysis Agent can only use a Python analysis tool if that tool is described by
a valid Skill Card. While, the Learning Pipeline is the offline subsystem that ingests
a raw Python function and produces such a Skill Card. It addresses the scalability
problem: as the number of JUNO analysis tools grows, manually authoring Skill Cards
becomes a bottleneck. Furthermore, manual Skill Card authoring would impose an
adoption cost on users. Overall, the Learning Pipeline reads a python function, extracts
what can be known deterministically, asks a language model to interpret the purpose of
the code, drafts a Skill Card, tests that card, and refines it when validation fails.
   The pipeline is implemented as a second LangGraph StateGraph, separate from
the Analysis Agent, with seven nodes organised into three phases: analysis (extracting
metadata from source code), synthesis (drafting the Skill Card and preparing test

scenarios), and validation (testing the draft against the Analysis Agent itself). This
separation mirrors the main difficulty of the task. Some information about a function
can be extracted mechanically from the source code, but other information requires
interpretation. The pipeline therefore combines deterministic program analysis with
LLM reasoning and then checks the result using explicit validation gates.

3.4.1    Pipeline State
All nodes in the Learning Pipeline communicate through a shared state object. Con-
ceptually, this state stores four categories of information:


   1. The input function, including its source code, module path, and name.

   2. Extracted evidence, such as the function parameters, docstring, analysis, and
      return types.

   3. The current Skill Card draft, which is updated by the drafter and refiner.

   4. Validation reports and simulation data, which record tests, their results and
      what should be repaired.


    The exact implementation contains additional fields used to route the graph and
store intermediate messages. The main idea is that the pipeline keeps the original
evidence, the current draft, and the validation feedback together so that each refinement
step can be grounded in previous results.


3.4.2    Phase 1: Analysis
The first phase tries to answer a basic question: what does this Python function appear
to do, and how is it called? The pipeline uses two complementary readers. The first
is deterministic and reads the code structure. The second is interpretive and uses a
language model to explain the function’s purpose.

Static Extraction Node

The StaticExtractionNode parses the target Python file into an Abstract Syntax
Tree (AST, a tree structure representation of code focusing on content and structure
instead of syntax) using Python’s built-in ast module and extracts information that
can be obtained without interpretation. This includes the function name, module path,
parameters, default values, type hints when present, docstring, imports, and visible
return statements. This information forms the factual basis of the Skill Card.
    This node is deliberately deterministic. If the function has an argument called
event_range, the extracted metadata must contain event_range, not a paraphrased
name such as “events”. This is essential because the final Skill Card must match the
real Python interface.

Neural Analysis Node

The Neural Analysis Node receives the source code and the static metadata, then asks
the language model to produce a short functional interpretation. It focuses on questions
such as:

  • What kind of diagnostic task does the function support?

  • What output should the Analysis Agent expect?

  • Are there implicit assumptions, such as required files, detector identifiers, or event
    ranges?

    The model is instructed to base its interpretation on the code and extracted metadata.
It, then, outputs fields (input requirements, functional summary,...) that will later be
used by the other nodes.


3.4.3     Phase 2: Synthesis
The synthesis phase takes the combined analysis output and produces two objects: a
draft Skill Card and a test plan with associated data.

Drafter Node

The Drafter Node builds the initial Skill Card. It receives the static extraction results,
the neural analysis, and the Skill Card schema described in Section 3.2. It is constrained
to conform its output exactly to the five-block schema described in Section 3.2.1. Its
prompt provides the LLM with the function name, its docstring, and the different fields
from the Neural analysis node. It also includes an example Skill Card to establish the
expected style and level of detail (Adding an example improves LLM performance [12]).

                                           38
                                                        3.4. THE LEARNING PIPELINE


    The Drafter Node is invoked in one of two modes. On the first iteration, it operates
from the raw analysis data. On subsequent iterations, triggered by a failed validation,
the prompt is augmented with two additional elements: the previous draft (so the LLM
can see what it produced) and the refinement feedback generated by the Refiner Node
(so it knows what to fix). This feedback re-drafting is the mechanism through which
the pipeline self-corrects.


Simulator Node

The SimulatorNode generates the test plan that the Gauntlet validation protocol
will execute. It produces a SimulationData object containing two test scenarios and,
optionally, mock data files. The last part refers to the face that the SimulatorNode
operates in one of two modes depending on whether the pipeline was invoked with real
test files or if a test file is needed:
  Real data mode. If the manual_test_files field is populated, the node instructs the
LLM to write scenarios referencing the provided file path. No mock data is generated.
   Mock data mode. If no test files are provided, the LLM generates minimal mock
CSV files with appropriate headers and a small number of rows. The prompt constrains
the LLM to use a consistent data framework. The mock data is not intended to be
realistic but it is intended to be structurally valid. It should suffice for the tool to
execute without crashing, so that the Gauntlet can assess whether the Skill Card’s
parameter schema enables correct invocation.


3.4.4     Phase 3: The Gauntlet Validation Protocol
The Gauntlet is a two-phase validation protocol that tests the draft Skill Card through
the Analysis Agent itself. Rather than checking the Skill Card’s fields statically (which
could verify syntax but not usability), the Gauntlet answers the question: can the agent
actually select, parameterise, and execute this tool correctly given realistic user queries?


Phase 1: Unit Testing (Isolation)

The ValidationUnitNode tests the draft Skill Card in an isolated environment where
it is the only tool available. This eliminates the distraction variable: if the agent fails
to select the tool when there is no alternative, the problem lies in the Skill Card’s
description or parameter schema.
    The node runs the simple scenario through a sequential gate protocol. The gates
are evaluated in order and failure at any gate halts evaluation of the following gates,
since their preconditions are not met.

                                            39
CHAPTER 3. SYSTEM DESIGN AND IMPLEMENTATION


Gate A — Isolation Selection. The scenario query is passed to the AgentNode.
The gate checks that the AgentNode selects the skill. Failure indicates that the Skill
Card’s description is too weak or too misaligned with the query for the agent to recognise
it as relevant, even when it is the only option.


Gate B — Argument Formatting. The selection message is passed to the
ArgumentFormatterNode. The gate checks that the ArgumentFormatterNode pro-
duces a valid tool call attribute . Failure indicates a schema mismatch: the parameter
types, required flags, or descriptions in the Skill Card are inconsistent enough that the
ArgumentFormatterNode either rejects the tool or cannot construct valid arguments.


Gate C — Execution. The validated tool call is passed to the ToolExecutor. The
gate checks that execution completes without returning an error. Failure indicates
a runtime incompatibility: the arguments produced by the ArgumentFormatterNode,
while schema-valid, are not semantically correct for the underlying function (e.g. a file
path that does not exist, or a parameter value outside the function’s acceptable range).


Gate D — Semantic Validity. If a tool’s return value is an empty result (empty
dictionary, empty list, or empty string), it indicates that the function was executed but
produced no useful output, which may signal an issue with the mock data.


Phase 2: Integration Testing (Production Environment)

Following a successfull unit test, the ValidationIntegrationNode tests the draft Skill
Card in the full production environment: a complete Analysis Agent graph loaded with
all existing production skills plus the draft.
    Both scenarios (simple and ambiguous) are executed against the full agent, which
is ran autonomously through its complete Select-then-Validate loop. After execution
completes, the node performs a post-analysis of the resulting message history, searching
for specific message types to evaluate :


Gate E — Integration Selection. The node searches the message history for the
most recent SelectSkill message and checks whether the selected skill matches the
draft’s name. If the agent selected a different tool, this constitutes a distraction failure:
the draft Skill Card’s description or usage policy was insufficiently distinctive relative
to a competing production tool. The gate records the name of the competing tool that
distracted the agent, which the Refiner Node uses to generate targeted feedback.

                                                       3.4. THE LEARNING PIPELINE


3.4.5     The Refiner
When the Gauntlet detects a failure, the RefinerNode analyses the validation reports
and generates targeted feedback that is routed back to the Drafter Node for a subsequent
synthesis iteration. The refinement mechanism distinguishes two failure classes and
produces different feedback for each.

Path 1: Unit Failures. If the unit test report indicates a failure, the Refiner Node
examines the failed gate and generates feedback specific to the failure type.

Path 2: Ambiguity Failures (Integration Test). If the unit test passed but
the integration test failed, the Skill Card is technically correct but insufficiently dis-
tinguishable from competing tools. The Refiner Node identifies the competing tool
that distracted the agent and loads its usage policy from the production registry. The
feedback instructs the Drafter Node to update the draft with updated information on
the conflicting skill.
The Refiner Node returns the feedback then routes back to the Drafter Node, which
re-drafts the Skill Card with the feedback injected into its prompt. The loop continues
until either all Gauntlet gates pass or a configurable maximum number of iterations is
reached.

4.1.2    Baseline Agent (B1)
The baseline agent, referred to as B1 throughout this chapter, is a standard ReAct [18]

4.1.4    Benchmark Design
Existing benchmarks for tool-using LLM agents are designed around standardized,
domain-agnostic tasks and cannot be applied directly to the JUNO evaluation prob-
lem. The Berkeley Function Calling Leaderboard (BFCL) [43] measures single-turn
function-calling accuracy on generic API signatures (e.g. weather queries, calendar
events). It tests argument formatting in isolation but not multi-step planning, memory

                                           43
CHAPTER 4. EXPERIMENTS AND RESULTS


management, or tool-chain reasoning. AgentBench [44] evaluates agents across diverse
environments (web browsing, database queries, operating system interaction) but none
of its tasks involve scientific tool orchestration or domain-specific hardware diagnostics.
ScienceAgentBench [45] gets close, as it targets data-driven scientific workflows, but
its evaluation protocol measures end-to-end code generation rather than tool selection
and argument correctness over an existing tool registry. More importantly, none of
these benchmarks captures the specific failure modes that matter in the JUNO context.
Evaluating the JUNO agent against BFCL or AgentBench would measure generic
function-calling competence of the underlying LLM, not the architectural contributions
that this thesis claims.
    A domain-specific benchmark was therefore designed to measure the capabilities
of the agent. The benchmark comprises 33 diagnostic queries organized into four
active tiers of increasing complexity, plus a set of four long-horizon scenarios evaluated
separately. Each query is specified as a JSON object containing the query text, the
expected tool or tool sequence, the expected arguments, and, where applicable, the
ground-truth result. This specification schema enables easy automated scoring against
deterministic criteria. Table 4.1 defines tiers 1,2,3 and 5 (Tier 4 being Long-horizon
scenarios explained in the next sub-section) and their design intent.
    The query specification schema supports several evaluation modes. The expected_tools
field lists the tool or tools that should be called; for queries with multiple valid ap-
proaches, the accepted_toolchains field provides a list of acceptable tool sequences.
The expected_args field specifies the argument values against which the agent’s output
is compared.


4.1.5     Long-Horizon Scenarios
To evaluate the agent’s ability to plan, execute, and synthesise results across extended
diagnostic workflows, four long-horizon scenarios (Tier 4) were designed. Each scenario
encodes a realistic diagnostic task with a known ground truth, requiring the agent to
autonomously determine the appropriate tool sequence, manage intermediate results,
and produce a final diagnostic conclusion.

Each query or scenario was executed N = 5 times. These repetitions are useful for
exposing stochastic failure modes and for descriptive robustness labels, but they are
not large enough to support precise estimates of production success probabilities or
strong claims about small differences between agents. The per-tier counts are therefore
reported descriptively, with Wilson 95% confidence intervals chosen because it provides

correct coverage for small N and for proportions near 0 or 1. The small differences
with overlapping intervals are interpreted as hypotheses for error analysis rather than

4.3.2     Failure Mode Analysis
Examination of the failed runs across both agents reveals four recurring failure modes,
categorised below. These categories are not mutually exclusive, a single failed run may
exhibit more than one.

Synthesis gap. The agent executes all required tool calls and obtains all intermediate
results, but fails to synthesise them into a correct final answer. This occurs when
the relevant finding is present in the message history but has been lost in context by
subsequent messages. The agent then produces a plausible but incomplete conclusion,
omitting the critical finding. This failure mode is characteristic of the baseline, which
has no memory compression to persist intermediate findings.

Structural boundary error. The agent misidentifies where one sub-task ends
and the next begins. For example, after completing the occupancy analysis phase of
Scenario D, the agent may attempt to conclude rather than proceeding to the hardware
tracing phase. This failure mode is related to plan management: the explicit plan
structure in the JUNO agent mitigates it (the agent can see that pending steps remain),
but it still occurs on Scenario D when the plan itself is poorly constructed. It can also
be linked to the reduced abilities of small LLM models.

Tool confusion under catalogue pressure. In the middle of a long chain, the
agent selects a semantically plausible but incorrect tool for an intermediate step. For
example, selecting scan_run_for_occupancy_anomalies (a windowed scanner) when
detect_global_occupancy_outliers (a global outlier detector) is required. The
validation node catches many of these errors, but not all.

False memory under tool-call pressure. After many sequential tool calls (typically
more than ten), the LLM begins to generate outputs that reference PMT identifiers,
scores, or file paths that do not appear in any tool output. This is a hallucination
failure mode exacerbated by context length. The Folded Memory system’s findings list

                                             4.4. LEARNING PIPELINE EVALUATION


mitigates this by providing a compact and high priority reference for specific values, but
it cannot prevent all instances, particularly when the hallucinated value is consistent
with the compressed summary.

Scenario D: a limit test. The JUNO agent achieves only 1/5 on Scenario D the four
failed runs exhibited a combination of structural boundary errors and tool confusion.
Scenario D was designed to probe the boundary of what the current model tier can
support with the available architectural scaffolding. The result confirms that cross-
subsystem reasoning chains of 15+ tool calls exceed the reliable operating envelope of
GPT-OSS 20B, even with plan structure, validation, and memory compression. This
finding defines the current capability ceiling and motivates future work on stronger
planning mechanisms or more capable local models.

Chapter 5

Conclusion and Perspectives

This thesis investigated to what extent a locally deployed LLM agent can orchestrate
detector analysis tools reliably enough to support JUNO-style diagnostic queries. The
motivation was not to replace expert physicists, but to reduce the operational distance
between a natural-language question and the execution of the appropriate analysis
pipeline. The work focused on two research questions: the design of a robust tool-using
architecture for a heterogeneous scientific tool suite, and the possibility of automatically
synthesising the tool descriptions required by that architecture.
    The main conclusion is that explicit structure matters. A generic ReAct agent
can use the same tools and the same underlying language model, but it lacks the
intermediate representations needed to make tool selection, argument construction,
memory management, and refusal behaviour separately controllable. The Skill Card
abstraction, the Select-then-Validate workflow, and Folded Memory address specific
failure modes observed in small local models: tool confusion, argument hallucination,
inference constraint and long-context degradation. The resulting system is slower than
the baseline, but substantially more reliable on the tasks for which scientific correctness
matters most.


5.1      Summary of Contributions

5.1.1     RQ1: Agent architecture and representation.
The first research question asked how a multi-node agent and a Skill Card abstraction
should be designed so that an LLM can robustly solve JUNO-style diagnostic queries
using existing tools. This thesis introduced a typed Skill Card schema that stores tool
identity, usage policy, argument contracts, execution metadata, and output structure
in a single human-readable document. It also introduced a Select-then-Validate agent
architecture implemented with LangGraph, in which tool selection is separated from
argument formatting and validation. This separation proved useful empirically. On the

                                            55
CHAPTER 5. CONCLUSION AND PERSPECTIVES


tiered benchmark, the JUNO agent matched the baseline on Tier 1 single-tool queries,
achieved 38/40 successful runs on Tier 3 multi-tool queries compared with 35/40 for
the baseline, and achieved 19/25 valid refusals on Tier 5 compared with 16/25 for the
baseline. The clearest difference appeared in Argument Correctness Rate: the JUNO
agent obtained ACR values of 1.00, 0.99, and 0.90 on Tiers 1–3, while the baseline
obtained 0.81, 0.75, and 0.83. These results support the central design claim: for small
local models, explicit validation and structured tool metadata reduce argument errors
more effectively than relying on a single tool-calling prompt.


Long-horizon diagnostic behaviour. The same architecture also improved long-
horizon performance. On the four extended diagnostic scenarios, the JUNO agent
completed 16/20 runs, whereas the ReAct baseline completed 3/20. The baseline’s
failures were not primarily caused by a lack of access to tools, but by the absence of
persistent state: it lost intermediate findings, produced premature final answers, or
failed to maintain a coherent multi-step plan. Folded Memory partially mitigated this
problem by preserving important findings outside the raw message history.


5.1.2     RQ2: In-context Skill learning.
The second research question asked whether Skill Cards could be automatically synthe-
sised from Python scripts while preserving agent performance. The Learning Pipeline
combined static analysis of function signatures and source code with LLM-based draft-
ing, testing, and refinement. In the comparative benchmark, auto-synthesised cards
produced performance close to hand-written cards. Tool Selection Rate was identical
on Tier 1 (50/50), quite similar for auto-synthesised cards on Tier 2 (42/50 versus
40/50) and Tier 3 (39/40 versus 38/40), but lower on Tier 5 refusal queries (16/25
versus 19/25). Argument correctness was also near-identical: 1.00, 0.99, and 0.90 for
hand-written cards, compared with 1.00, 0.98, and 0.91 for auto-synthesised cards.
These results indicate that the Learning Pipeline can achieve similar performance in
schema parametering. The Tier 5 results suggest that negative usage boundaries may
be harder to learn automatically, although the small sample size prevents this from
being treated as a definitive conclusion.



5.2      Limitations
The first limitation is the scale and representativeness of the benchmark. The tiered
benchmark contains 33 diagnostic queries, each executed five times, and the long-horizon
evaluation contains four scenarios. This is sufficient to expose recurring architectural
failure modes, but it is not large enough to estimate absolute success probabilities with

                                           56
                                                                       5.2. LIMITATIONS


high precision. The results should be interpreted as evidence about controlled diagnostic
tasks rather than as a complete measure of production reliability. Furthermore, there is
the absence of a component-level ablation of the Skill Card fields. The thesis argues that
Skill Cards are useful because they combine parameter schemas, usage policies, execution
metadata, and output schemas in a single representation. However, the evaluation
compares complete agent configurations rather than removing each field independently.
As a result, the experiments support the usefulness of the combined Skill Card based
architecture, but they do not establish the individual contribution of usage_policy,
output_schema, or the parameter schema in isolation. A targeted ablation, for example
removing usage_policy while keeping the rest of the card unchanged, would be needed
to quantify these contributions. The intended sample size, which was was supposed to
be bigger than 5, and this experiment could not be made before submission because the
hardware server used for the benchmark became unavailable after the main evaluation
runs.
   The second limitation is the scope of the tool suite. The implemented tools are
representative of JUNO diagnostic workflows and use JUNO hardware nomenclature,
but they do not cover the full operational analysis ecosystem of the experiment. The
input data are also simplified relative to the complete production data model. The
thesis therefore evaluates the agent’s ability to orchestrate a realistic and executable
diagnostic tool suite, not its readiness to cover all detector-operation tasks.
    The third limitation concerns the model tier. The system was deliberately evaluated
with locally deployed open-weight models, reflecting the constraints of restricted scientific
computing environments. This makes the results practically relevant, but also model-
specific. Stronger local models, better structured-output capabilities, or faster inference
backends could change both the success rates and the latency trade-off. The architecture
itself is model-agnostic, but the numerical results are not.
    The fourth limitation is latency. The JUNO agent is consistently slower than the
baseline because it performs multiple LLM calls per tool iteration: one for selection,
one for formatting and validation, and additional calls for memory compression when
required. This cost is acceptable for offline diagnostic support, where correctness is
more important than immediate response time. It would not yet be acceptable for
real-time detector monitoring or DAQ-level intervention.
    The final limitation concerns the Learning Pipeline. Static analysis can extract
function names, parameters, defaults, type hints, and some usage evidence from source
code, but it cannot fully infer detector semantics. Valid PMT ranges, physical units,
calibration assumptions, and negative usage policies often depend on expert knowledge
outside the Python function itself. The Learning Pipeline can reduce the effort required
to create Skill Cards, but it should remain embedded in a human-in-the-loop workflow
for scientific use.

CHAPTER 5. CONCLUSION AND PERSPECTIVES


5.3      Future Work
A first direction is evaluation with stronger local models. The present architecture was
designed around the limitations of small open-weight models, and the results show both
the value and the limits of that approach. Repeating the benchmark across several model
sizes would clarify which failures are architectural and which are model-capability limits.
Scenario D, in particular, should be revisited with stronger planning and long-context
models, since it currently defines the upper boundary of the system’s reliable operating
abilities.
   A second direction is a benchmark ablation of the Skill Card representation and the
Analysis Agent architecture. For the Skill card, future experiments should compare :
parameter schema only, parameter schema plus usage policy, and the full Skill Card.
    A third direction is a stronger planning layer. The current agent keeps an explicit
plan, but the plan is still generated and revised by the same local LLM that performs
tool selection. Long-horizon failures show that the system sometimes misidentifies
sub-task boundaries or concludes before all required checks have been completed. A
more robust planner could represent tasks as structured steps, enforce completion
criteria for each sub-task, and verify that every required diagnostic question has been
answered before producing a final response.
    A fourth direction is extension toward online diagnostic support. The current
system is intentionally offline: it answers questions about existing files and completed
or ongoing runs. Moving toward online use would require integration with monitoring
infrastructure, faster local inference, stricter execution safeguards, and human approval
for any action with operational consequences. The most realistic intermediate step is
not full autonomy, but a watch-mode assistant that periodically summarises detector
conditions, flags anomalies, and proposes follow-up tools for expert approval.
    A fifth direction is improvement of the Learning Pipeline. The current pipeline can
synthesise useful Skill Cards from Python source code, but negative usage policies and
semantic constraints remain weak points. Future versions should incorporate richer test
generation, explicit unit and range inference, examples from historical tool usage, and
human-in-the-loop correction. A useful practical target would be a review interface in
which the system drafts a Skill Card, highlights uncertain fields, and asks the physicist
to approve or correct only the parts that cannot be inferred reliably.
    A final direction is cross-experiment transfer. Many large detector experiments
face similar problems: heterogeneous tool ecosystems, specialised hardware hierarchies,
restricted computing environments, and a need for traceable diagnostic reasoning. The
Skill Card abstraction is not specific to JUNO. Applying the same approach to another
experiment would test whether the architecture generalises beyond the particular tool
suite and data format used in this thesis. Such a transfer study would also clarify which

                                            58
                                                             5.4. CLOSING REMARKS


parts of the system are domain-independent and which require experiment specific
design.


5.4      Closing Remarks
The central lesson of this thesis is that reliable scientific agents can’t simply rely on
a basic tool access. They require explicit representations of what tools mean, when
they should be used, how their arguments should be validated, and how intermediate
findings should persist across a diagnostic chain. In this work, Skill Cards provide
that representation, Select-then-Validate provides the execution, and Folded Memory
provides the state-management mechanism needed for longer analyses.
    The resulting system is not a finished operational assistant for JUNO. It is a
prototype with clear limitations in scale, latency, model robustness, and evaluation
coverage. Nevertheless, the experiments show that a small local model, when supported
by the right structure, can perform useful scientific tool orchestration beyond what
a generic ReAct baseline can reliably achieve. This makes the approach a credible
foundation for future detector-analysis assistants: not autonomous replacements for
experts, but structured interfaces through which experts can query, combine, and audit
their own analysis tools more efficiently.

C.1      Memory Compression Ablation
The Folded Memory system (Section 3.3.5) compresses the message history periodically,
extracting key findings into a persistent list and replacing the raw history with a
compressed narrative summary. The compression frequency (every N tool calls) is
a configurable parameter. This section reports an ablation study that varies N to
determine its effect on long-horizon task completion.


C.1.1     Experimental Design
Five compression frequencies were tested: N ∈ {1, 3, 6, 9, 12}. For each frequency, all
four long-horizon scenarios (A–D) were executed Nruns = 5 times. All other variables
were held constant. N = 1 represents compression after every tool call.


C.1.2     Results
Figure C.1 plots the task completion rate as a function of compression frequency.
   The relationship between compression frequency and task completion exhibits an
inverted-U shape, with a clear optimum at N = 3. Table C.1 reports the numerical
values.

70%, which is below the optimum despite maximising the number of compression
opportunities. Two mechanisms degrade performance at this frequency. First, each
compression cycle involves a full LLM call to the Memory Folder Node, which adds one
inference call per tool invocation. For a 16-step scenario, this adds 16 additional LLM
calls, substantially increasing total latency and token consumption. Second, and more

Prompt Design and Development

The architecture described in Chapter 3 relies not only on the graph topology and
Skill Card representation, but also on prompt templates that define the role of each
LLM-based node. These prompts were not written as generic instructions. The prompt
templates were designed iteratively during implementation by observing recurring fail-
ures; but they were also informed by established prompt-engineering practices reported
in the literature. In particular, recent surveys and prompt pattern catalogues recommend
making the model’s role explicit, decomposing complex tasks into smaller reasoning
steps, separating instructions from context, providing structured input sections, and
constraining the expected output format [46].
   The final prompts follow three design principles.


Role separation. Each LLM node is assigned a narrow operational role. The Agent-
Node is prompted as a manager responsible for planning and tool selection. The
Argument Formatter Node is prompted as a specialist responsible for validating one
selected skill and constructing its arguments. The Memory Folder Node is prompted as
a compressor responsible for extracting persistent facts and summarising previous steps.


Context structuring. The prompts are organised into explicitly labelled context
blocks. For the AgentNode, the input context contains the original user query, compact
Skill Card summaries, the folded memory summary, confirmed findings, the current
plan, and recent message history. This formatting was chosen to reduce ambiguity
about where information should be retrieved from. .


Constrained output. Each LLM node is coupled to a Pydantic structured-output
model. Thus, the prompt does not ask for arbitrary natural language, but for a JSON
object matching a predefined schema. For the AgentNode, the model must return either
a tool-selection decision or a final answer. For the Formatter Node, it must return either
